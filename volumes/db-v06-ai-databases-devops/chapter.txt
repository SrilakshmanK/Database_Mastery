
A production AI system might need to store:

```text

Documents
Chunks
Embeddings
Conversations
Messages
Tool calls

Evaluation results

```

These data types don't necessarily have the same storage requirements.

---

# 1.2 Example Architecture

```text
                    AI BACKEND
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
   PostgreSQL        Redis            Object Storage
        │               │                │

     pgvector
        │
        ▼
    Embeddings
```

The important architectural idea:

> **Not every piece of data belongs in the same storage system.**

# 1.3 Source of Truth

For every important piece of data, define:

```text
Where is the authoritative copy?
```

Example:

```text
User account
→ PostgreSQL

Original PDF
→ Object storage

Document metadata
→ PostgreSQL

Embedding
→ PostgreSQL + pgvector

Cached response
→ Redis
```

This prevents architecture confusion.

# CHAPTER 03 — EMBEDDINGS AS DATABASE DATA

An embedding is a numerical representation of information.

For example:

```text
Text
 ↓
Embedding Model
 ↓
[0.13, -0.42, 0.81, ...]
```

The result is a vector.

---

# 3.1 Why Store Embeddings?

Suppose we have:

```text
Document A
Document B
Document C
```

Each gets an embedding:

```text
A → vector A
B → vector B
C → vector C
```

When the user asks a question:

```text
Question
 ↓
Vector Q
```

We compare:

```text
Q ↔ A
Q ↔ B
Q ↔ C
```

and retrieve the most similar content.

---

# 3.2 Database Record

A useful conceptual model:

```text
document_chunks
-------------------------
id
document_id
chunk_text
embedding
metadata
created_at
```

Now the database stores both:

```text
semantic representation
+
retrievable content
```

---

# 3.3 Important Principle

An embedding is **derived data**.

The original document/chunk is the source of truth for the text.

If the embedding disappears:

```text
chunk
 ↓
re-embed
 ↓
new vector
```

Therefore:

> Don't treat embeddings as irreplaceable source data.

---

# 3.4 Embedding Model Version

Store the embedding model/version used.

For example:

```text
embedding_model
embedding_dimensions
embedding_version
```

Why?

Because changing embedding models can change vector dimensions and similarity behavior.

---

# CHAPTER 04 — POSTGRESQL + PGVECTOR

PostgreSQL can store vector data using:

> pgvector

Conceptually:

```text
PostgreSQL
    +
pgvector
    ↓
Relational + Vector Database
```

---

# 4.1 Why This Is Powerful

You can store:

```text
User
Document
Permissions
Metadata
Chunk
Embedding
```

in one PostgreSQL environment.

This can simplify systems significantly.

---

# 4.2 Vector Column

Conceptually:

```sql
CREATE TABLE document_chunks (
    id BIGSERIAL PRIMARY KEY,
    document_id BIGINT NOT NULL,
    content TEXT NOT NULL,
    embedding VECTOR(1536)
);
```

The exact dimension depends on the embedding model.

Do not blindly use `1536`.

The vector dimension must match the embedding model.

---

# 4.3 Extension

pgvector is installed/enabled as a PostgreSQL extension.

Conceptually:

```sql
CREATE EXTENSION vector;
```

The exact installation procedure depends on your PostgreSQL environment.

---

# 4.4 Relational + Vector Data

This is where pgvector becomes especially useful.

Example:

```text
document_chunks
│
├── document_id
├── tenant_id
├── content
├── category
├── created_at
└── embedding
```

Now vector search can be combined with ordinary SQL filtering.

# CHAPTER 05 — VECTOR SIMILARITY SEARCH

The database must compare vectors.

Common similarity/distance concepts include:

```text
Cosine distance
Euclidean distance
Inner product
```

---

# 5.1 Cosine Similarity

Conceptually:

```text
A · B
────────────
|A| × |B|
```

It measures directional similarity.

---

# 5.2 Euclidean Distance

Conceptually:

```text
distance(A,B)
=
sqrt(
 (a1-b1)^2 +
 (a2-b2)^2 +
 ...
)
```

Smaller distance means closer vectors.

---

# 5.3 Inner Product

Another measure of vector relationship.

The correct metric depends on:

* embedding model
* normalization
* application requirements

---

# 5.4 Nearest Neighbor Search

Suppose:

```text
Query vector
      ↓
Compare against vectors
      ↓
Rank by distance
      ↓
Return top K
```

This is:

> Nearest-neighbor search.

---

# 5.5 Example Mental Model

```text
Query
 ↓
Vector
 ↓
Vector database
 ↓
Distance calculation
 ↓
Top K
```

---

# CHAPTER 06 — VECTOR INDEXING & SEARCH PERFORMANCE

Searching every vector becomes expensive at scale.

Suppose:

```text
10 million vectors
```

A naive approach might compare against every vector.

That's expensive.

Vector indexes help reduce search work.

---

# 6.1 Approximate Nearest Neighbor

Many vector indexes trade:

```text
exactness
```

for:

```text
speed
```

This is called:

> Approximate Nearest Neighbor (ANN).

---

# 6.2 HNSW

One important vector indexing approach is:

> HNSW — Hierarchical Navigable Small World.

You do not need to become an algorithm specialist.

Understand:

```text
Vector dataset
      ↓
HNSW index
      ↓
Approximate nearest neighbors
      ↓
Fast retrieval
```

---

# 6.3 IVFFlat

Another approach is:

> IVFFlat.

Conceptually:

```text
Vectors
 ↓
Clusters / lists
 ↓
Search selected areas
```

---

# 6.4 Trade-Off

Vector indexing involves:

```text
Recall
+
Latency
+
Memory
+
Index build cost
+
Storage
```

More aggressive approximate search may improve speed while potentially reducing recall.

---

# 6.5 Measure Retrieval Quality

Do not optimize only for:

```text
milliseconds
```

Also measure:

```text
retrieval quality
recall
precision
relevance
```

AI database performance has both:

```text
system performance
+
retrieval quality
```

---

# CHAPTER 07 — METADATA FILTERING & HYBRID RETRIEVAL

Pure vector similarity is often insufficient.

Suppose the user asks:

> Find documents about Kubernetes from the Engineering department.

Vector similarity alone may retrieve irrelevant documents.

We need metadata filtering.

---

# 7.1 Metadata

Store:

```text
tenant_id
user_id
department
document_type
created_at
permissions
tags
```

---

# 7.2 Filter + Vector Search

Conceptually:

```text
Query
 ↓
Metadata filter
 ↓
Vector similarity
 ↓
Top K
```

For example:

```sql
WHERE tenant_id = 42
  AND document_type = 'engineering'
```

plus vector similarity ranking.

---

# 7.3 Why Filtering Matters

Without filtering:

```text
Tenant A
Tenant B
Tenant C
```

could all be searched together.

That can create a serious security problem.

Therefore:

> **Authorization filtering is part of retrieval architecture.**

---

# 7.4 Hybrid Search

Vector search captures semantic similarity.

Keyword/full-text search captures exact terms.

Hybrid retrieval combines them:

```text
Keyword Search
       +
Vector Search
       ↓
Fusion
       ↓
Final Ranking
```

This is particularly useful for:

* product names
* IDs
* technical terms
* exact error messages
* semantic concepts

```text

document_chunks
----------------
id

```

Relationship:

```text
documents
    │
    └── document_chunks
```

---

# 8.2 Why Separate Documents and Chunks?

One document may produce:

```text
Document
 ↓
100 chunks
```

Therefore:

```text
documents
1 row

document_chunks
100 rows
```

This makes lifecycle management easier.

---

# 8.3 Chunk Identity

Each chunk should have a stable identity.

Useful fields:

```text
document_id
chunk_index
chunk_id
```

---

# 8.4 Metadata

Metadata can include:

```text
page_number
section
source
author
created_at
tenant_id
permissions
document_type
```

This improves:

* filtering
* citations
* debugging
* access control
* retrieval analysis

---

# 8.5 Document Updates

Suppose a document changes.

Old embeddings may become invalid.

A safe lifecycle:

```text
Document updated
      ↓
Mark old chunks stale
      ↓
Parse new document
      ↓
Create new chunks
      ↓
Generate embeddings
      ↓
Index new chunks
      ↓
Activate new version
```

This avoids partially updated retrieval data.

# CHAPTER 09 — DOCUMENT & CHUNK DATA MODELING

Chunking creates a database design problem.

---

# 9.1 Don't Store Only the Vector

Bad:

```text
id
embedding
```

You lose important context.

Better:

```text
id
document_id
content
embedding
metadata
```

---

# 9.2 Document Versioning

Useful model:

```text
documents
    ↓
document_versions
    ↓
chunks
```

This supports:

```text
old version
new version
```

and controlled re-indexing.

---

# 9.3 Soft Delete

For AI systems, immediate physical deletion can sometimes make debugging and recovery harder.

A soft-delete field may be useful:

```text
deleted_at
```

Then retrieval can filter:

```text
deleted_at IS NULL
```

But retention/privacy requirements must determine whether data should actually be permanently deleted.

---

# 9.4 Tenant Isolation

Multi-tenant AI applications should generally include tenant ownership in the data model.

Example:

```text
tenant_id
```

Every retrieval query must respect it.

# 10.2 Why Separate Messages?

* analytics

# 10.3 Conversation Memory

Not every message must be placed into the LLM context.

Database storage and model context are different things.

Think:

```text

Context window
→ current model input
```

The application selects relevant information.

---

# 10.4 Redis for Short-Term State

Redis may store:

```text

```

for:

* temporary workflow state
* rate limits
* active sessions
* short-lived caches

But durable conversation history can remain in PostgreSQL.

# CHAPTER 12 — REDIS IN AI APPLICATIONS

Redis becomes particularly useful in AI systems because model calls can be expensive and slow.

---

# 12.1 Cache Model Results

Potential architecture:

```text
User Query
   ↓
Normalize
   ↓
Cache?
 ┌───────┴───────┐
 HIT             MISS
 ↓                ↓
Response          LLM
                  ↓
                Cache
```

---

# 12.2 Cache Key

A model response cache key may depend on:

```text
model
prompt/version
input
parameters
retrieval context
```

A simplistic key like:

```text
query text
```

may be unsafe if different users or contexts produce different answers.

---

# 12.3 User Isolation

Never allow:

```text
User A
 ↓
cached response
 ↓
User B
```

unless the result is intentionally shared.

AI caching must account for:

```text
tenant
user
permissions
model
prompt version
retrieval context
```

---

# 12.4 Rate Limiting

AI APIs are expensive.

Redis can enforce:

```text
requests/minute
tokens/minute
cost/day
```

depending on how the application tracks usage.

# CHAPTER 13 — AI CACHING & SEMANTIC CACHE CONCEPTS

Traditional cache:

```text
exact key
```

AI requests can be semantically similar.

For example:

```text
"What is Docker?"
```

and:

```text
"Explain Docker."
```

may be semantically similar.

A semantic cache attempts to reuse results based on similarity rather than exact equality.

---

# 13.1 Semantic Cache

Conceptually:

```text
Query
 ↓
Embedding
 ↓
Similarity search
 ↓
Similar previous query?
 ├── yes → cached response
 └── no → LLM
```

---

# 13.2 Risks

Semantic caching can return an incorrect result if similarity is too loosely defined.

Therefore:

```text
similarity threshold
+
scope
+
freshness
+
authorization
```

matter.

---

# 13.3 Don't Cache Everything

Responses depending on:

* current time
* current user state
* private documents
* dynamic data

may not be safely reusable.

# CHAPTER 14 — DATABASE MIGRATIONS & SCHEMA EVOLUTION

Production databases change.

Example:

```text
Version 1
users(name)

Version 2
users(first_name, last_name)
```

The database must evolve without breaking the application.

---

# 14.1 Migration

A migration is a version-controlled database change.

Example:

```text
001_create_users.sql
002_create_products.sql
003_add_user_status.sql
```

---

# 14.2 Why Git?

Database structure should be versioned alongside application code.

```text
Application Version
        +
Database Migration Version
```

must remain compatible.

---

# 14.3 Migration History

A migration system usually records:

```text
migration version
timestamp
applied status
```

so the environment knows which migrations have executed.

---

# 14.4 Never Manually Change Production Without Tracking It

Bad:

```text
Production database
↓
random manual SQL
```

Now development/staging may not match production.

Better:

```text
Migration
 ↓
Git
 ↓
CI/CD
 ↓
Database
```

---

# CHAPTER 15 — MIGRATION SAFETY & ZERO-DOWNTIME CHANGES

Schema changes can break running applications.

---

# 15.1 Dangerous Example

Application version A expects:

```text
name
```

Migration immediately removes:

```text
name
```

before version B is deployed.

Application A breaks.

---

# 15.2 Expand-and-Contract

Use:

```text
Phase 1
Add new field
```

Then:

```text
Phase 2
Deploy application that supports both
```

Then:

```text
Phase 3
Backfill data
```

Then:

```text
Phase 4
Switch reads/writes
```

Finally:

```text
Phase 5
Remove old field
```

---

# 15.3 Example

Old:

```text
full_name
```

New:

```text
first_name
last_name
```

Safe evolution:

```text
Add first_name
Add last_name
        ↓
Application writes both
        ↓
Backfill old records
        ↓
Application reads new fields
        ↓
Verify
        ↓
Remove full_name later
```

---

# 15.4 Migration Checklist

Before production:

```text
Does migration lock?
How long might it run?
Is it backward compatible?
Is rollback possible?
Does it require data backfill?
How large is the table?
What happens under live traffic?
```

# CHAPTER 16 — DATABASE TESTING

Database code must be tested.

---

# 16.1 Unit Testing

Test application-level logic.

---

# 16.2 Integration Testing

Run against a real database.

This catches:

* SQL errors
* constraint issues
* migration problems
* transaction bugs
* query differences

---

# 16.3 Test Database

Use a separate database:

```text
development
testing
production
```

Never run destructive tests against production.

---

# 16.4 Seed Data

Create reproducible test data.

Example:

```text
test user
test products
test orders
```

---

# 16.5 Migration Testing

CI should be able to:

```text
Create empty DB
 ↓
Run all migrations
 ↓
Seed data
 ↓
Run tests
```

If migrations cannot build a clean database, there is a deployment problem.

---

# 16.6 Rollback Testing

Where rollback is supported/appropriate, test it.

But don't assume every production migration can be safely reversed.

Sometimes the safer strategy is a forward corrective migration.

# CHAPTER 22 — BACKUP, RECOVERY & DISASTER PLANNING

AI databases contain valuable information.

Backup strategy must cover:

```text

Configuration
Migration history
```

---

# 22.1 Source vs Derived Data

This distinction is extremely useful.

Example:

```text
Original PDF
   ↓
Chunk
   ↓
Embedding
```

Potentially:

```text
PDF = source
Chunk = derived
Embedding = derived
```

If embeddings disappear:

```text
recompute
```

If the original document disappears:

```text
data may be irrecoverable
```

Therefore backup priorities differ.

---

# 22.2 Backup Strategy

For PostgreSQL:

```text
logical backups
+
physical backups
+
WAL/PITR where appropriate
```

For MongoDB:

```text
managed backup
or
appropriate dump/snapshot strategy
```

For Redis:

```text
depending on its role
```

A cache may not require the same recovery strategy as durable business data.

---

# 22.3 Restore Testing

Do not say:

> "We have backups."

Say:

> "We have successfully restored backups and verified application state."

---

# 22.4 Disaster Recovery

Document:

```text
What failed?
Where is backup?
How do we restore?
How long?
What data could be lost?
What dependencies are required?
Who performs the recovery?
```
