# CHAPTER 01 — HOW TO THINK ABOUT SQL PROBLEMS

The biggest mistake beginners make is starting with syntax.

They see:

> "Find the top five customers by revenue."

and immediately start typing:

```sql
SELECT ...
```

Don't.

First translate the question.

---

# 1.1 Identify the Result

Question:

> Find the top five customers by total spending.

What should one result row represent?

```text
One customer
```

What information do we need?

```text
customer_id
customer_name
total_spending
```

---

# 1.2 Identify the Source Data

We might need:

```text
customers
orders
order_items
products
```

But perhaps only:

```text
customers
orders
```

depending on the schema.

The query should use only what is necessary.

---

# 1.3 Identify the Relationship

For example:

```text
customers
    ↓
orders
```

```text
customer.id
      =
orders.customer_id
```

---

# 1.4 Identify the Calculation

Total spending might be:

```text
SUM(order.amount)
```

---

# 1.5 Identify the Ranking

```text
ORDER BY total_spending DESC
LIMIT 5
```

Only after thinking through all of this should we write SQL.

---

# 1.6 The Query Design Template

For many problems:

```text
1. What should one row represent?
2. Which tables are required?
3. How are they related?
4. Which rows should be included?
5. Which columns should be returned?
6. What calculations are required?
7. Do we need grouping?
8. Do we need ranking?
9. Are there edge cases?
10. Is performance important?
```

This thinking is more valuable than memorizing syntax.

---

# CHAPTER 02 — RELATIONAL QUERY THINKING

SQL works naturally with sets of rows.

Think in terms of:

```text
Input relation
      ↓
Transformation
      ↓
Output relation
```

For example:

```text
orders
  ↓
filter completed orders
  ↓
group by customer
  ↓
calculate revenue
  ↓
sort
  ↓
top customers
```

---

# 2.1 Don't Think Only Row-by-Row

Procedural thinking:

```text
for each order:
    find customer
    add amount
```

SQL thinking:

```text
SELECT ...
FROM orders
GROUP BY customer_id
```

The database works with sets.

This is one of the biggest mental shifts in SQL.

---

# 2.2 Intermediate Results

Complex SQL becomes easier when you imagine intermediate tables.

For example:

```text
orders
   ↓
completed_orders
   ↓
customer_totals
   ↓
ranked_customers
   ↓
top_5
```

CTEs later give us a clean way to represent this reasoning.

---

# 2.3 Query Correctness

Always ask:

> What does one row in my result represent?

If you cannot answer that, your query probably isn't fully understood.

This is the **grain** of the result.

---

# 2.4 Grain

Example:

```text
One row per customer
```

versus:

```text
One row per order
```

versus:

```text
One row per order item
```

Mixing these levels accidentally causes many SQL bugs.

---

# CHAPTER 03 — ADVANCED JOIN REASONING

Joins are not just syntax.

They represent relationships between sets.

---

# 3.1 INNER JOIN

Suppose:

```text
customers
orders
```

Query:

```sql
SELECT
    c.id,
    c.name,
    o.id AS order_id
FROM customers c
JOIN orders o
    ON o.customer_id = c.id;
```

Result:

> Customers that have matching orders.

---

# 3.2 LEFT JOIN

```sql
SELECT
    c.id,
    c.name,
    o.id AS order_id
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.id;
```

Result:

> Every customer, plus matching orders where they exist.

---

# 3.3 Classic Mistake

Consider:

```sql
SELECT
    c.id,
    c.name,
    o.id
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.id
WHERE o.status = 'completed';
```

The `WHERE` condition removes rows where `o` is NULL.

The query may effectively behave like an inner join.

If you want to preserve customers without orders while restricting the joined rows:

```sql
SELECT
    c.id,
    c.name,
    o.id
FROM customers c
LEFT JOIN orders o
    ON o.customer_id = c.id
   AND o.status = 'completed';
```

Understanding **where conditions are applied** is crucial.

---

# 3.4 Join Multiplication

Suppose:

```text
Customer A
   ↓
3 orders
```

and each order has:

```text
4 order items
```

Joining everything can produce:

```text
3 × 4 = 12 rows
```

This may cause incorrect aggregates if you don't understand the result grain.

---

# 3.5 Incorrect Revenue

Imagine joining:

```text
customers
orders
order_items
```

and then calculating:

```sql
SUM(orders.total)
```

If every order has multiple order items, the order total may appear multiple times.

This can inflate revenue.

The lesson:

> **Always understand row multiplication before aggregating.**

---

# 3.6 Join Debugging

When an aggregate looks suspicious:

1. Remove the aggregate.
2. Select the IDs.
3. Inspect row duplication.
4. Determine the result grain.
5. Fix the relationship.
6. Add aggregation again.

This is a powerful debugging technique.

# CHAPTER 04 — SUBQUERIES DEEP DIVE

Subqueries allow one query to use the result of another.

---

# 4.1 Scalar Subquery

Find products above average price:

```sql
SELECT
    id,
    name,
    price
FROM products
WHERE price > (
    SELECT AVG(price)
    FROM products
);
```

The inner query produces one value.

---

# 4.2 IN

Find customers who placed an order:

```sql
SELECT *
FROM customers
WHERE id IN (
    SELECT customer_id
    FROM orders
);
```

---

# 4.3 EXISTS

Often we care only whether a matching row exists:

```sql
SELECT *
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
);
```

Conceptually:

> Does this customer have at least one matching order?

---

# 4.4 NOT EXISTS

Find customers without orders:

```sql
SELECT *
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
);
```

This is an important real-world pattern.

---

# 4.5 Correlated Subquery

The inner query references the outer query.

```sql
SELECT
    c.id,
    c.name
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
);
```

The inner query depends on each outer customer.

---

# 4.6 Subquery vs JOIN

Many problems can be solved using either.

The question is not:

> "Which syntax is cooler?"

Ask:

> Which form expresses the intended logic clearly and performs appropriately?

We will compare plans in later chapters.

---

# CHAPTER 05 — COMMON TABLE EXPRESSIONS

CTEs use:

```sql
WITH
```

to create named intermediate query results.

---

# 5.1 Basic CTE

```sql
WITH completed_orders AS (
    SELECT *
    FROM orders
    WHERE status = 'completed'
)
SELECT *
FROM completed_orders;
```

This improves readability.

---

# 5.2 Multi-Step Query

```sql
WITH completed_orders AS (
    SELECT *
    FROM orders
    WHERE status = 'completed'
),
customer_totals AS (
    SELECT
        customer_id,
        SUM(amount) AS total_spent
    FROM completed_orders
    GROUP BY customer_id
)
SELECT *
FROM customer_totals
ORDER BY total_spent DESC;
```

Now the query reads almost like the reasoning process:

```text
completed orders
        ↓
customer totals
        ↓
ranking
```

---

# 5.3 Why CTEs Matter

They help with:

* readability
* decomposition
* debugging
* multi-stage transformations

But don't assume:

> CTE = automatically faster.

CTEs are primarily a query organization tool.

Performance depends on PostgreSQL's execution strategy and query structure.

---

# 5.4 CTE as a Debugging Tool

Develop the query incrementally:

```text
Step 1 → completed_orders
Step 2 → customer_totals
Step 3 → ranked_customers
```

Test each intermediate result.

This is excellent deliberate practice.

---

# CHAPTER 06 — RECURSIVE QUERIES

Recursive CTEs solve hierarchical problems.

---

# 6.1 Example

Imagine:

```text
CEO
 ├── Manager A
 │    ├── Employee 1
 │    └── Employee 2
 └── Manager B
      └── Employee 3
```

Data:

```text
employees
----------------
id
name
manager_id
```

The relationship forms a tree.

---

# 6.2 Recursive Structure

Conceptually:

```sql
WITH RECURSIVE employee_tree AS (
    -- base case
    SELECT
        id,
        name,
        manager_id
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- recursive case
    SELECT
        e.id,
        e.name,
        e.manager_id
    FROM employees e
    JOIN employee_tree t
        ON e.manager_id = t.id
)
SELECT *
FROM employee_tree;
```

---

# 6.3 Important Concept

Recursion has:

```text
Base case
+
Recursive step
```

Without a terminating condition or finite data structure, recursion can become problematic.

---

# 6.4 When to Use

Useful for:

* organizational hierarchies
* category trees
* folder structures
* dependency graphs
* hierarchical relationships

Do not use recursion merely because SQL supports it.

---

# CHAPTER 07 — SET OPERATIONS

SQL allows combining result sets.

---

# 7.1 UNION

```sql
SELECT email FROM customers
UNION
SELECT email FROM suppliers;
```

Removes duplicates.

---

# 7.2 UNION ALL

```sql
SELECT email FROM customers
UNION ALL
SELECT email FROM suppliers;
```

Keeps duplicates.

`UNION ALL` is often preferable when deduplication is not required because it avoids unnecessary duplicate elimination.

---

# 7.3 INTERSECT

Returns rows appearing in both results.

```sql
SELECT email FROM customers
INTERSECT
SELECT email FROM newsletter_subscribers;
```

---

# 7.4 EXCEPT

Returns rows from the first result that aren't in the second.

```sql
SELECT email FROM customers
EXCEPT
SELECT email FROM blocked_users;
```

---

# 7.5 Why Set Operations Matter

They are useful for:

* comparisons
* reconciliation
* reporting
* data validation

---

# CHAPTER 08 — CONDITIONAL LOGIC & DATA TRANSFORMATION

SQL can transform data as part of queries.

---

# 8.1 CASE

```sql
SELECT
    name,
    price,
    CASE
        WHEN price < 1000 THEN 'Budget'
        WHEN price < 5000 THEN 'Mid-range'
        ELSE 'Premium'
    END AS price_category
FROM products;
```

---

# 8.2 Conditional Aggregation

Very useful.

```sql
SELECT
    COUNT(*) AS total_orders,
    COUNT(*) FILTER (WHERE status = 'completed') AS completed_orders,
    COUNT(*) FILTER (WHERE status = 'cancelled') AS cancelled_orders
FROM orders;
```

PostgreSQL's `FILTER` syntax is useful for analytical queries.

Equivalent logic can also be written using `CASE`.

---

# 8.3 Conditional SUM

```sql
SELECT
    SUM(
        CASE
            WHEN status = 'completed'
            THEN amount
            ELSE 0
        END
    ) AS completed_revenue
FROM orders;
```

---

# 8.4 Data Transformation Principle

SQL isn't only retrieving data.

It can:

```text
Filter
Transform
Aggregate
Rank
Compare
Classify
Combine
```

This is why SQL is powerful for data engineering.

---

# CHAPTER 09 — ADVANCED AGGREGATION

Aggregation becomes much more interesting when answering real business questions.

---

# 9.1 Multiple Dimensions

Suppose:

```text
orders
customer_id
product_id
amount
created_at
```

You might ask:

> Revenue by month and category.

This requires multiple grouping dimensions.

---

# 9.2 GROUP BY Multiple Columns

```sql
SELECT
    category_id,
    DATE_TRUNC('month', created_at) AS month,
    SUM(amount) AS revenue
FROM orders
GROUP BY
    category_id,
    DATE_TRUNC('month', created_at);
```

---

# 9.3 COUNT DISTINCT

```sql
SELECT COUNT(DISTINCT customer_id)
FROM orders;
```

This answers:

> How many unique customers placed orders?

---

# 9.4 Aggregation Grain

Always know what one row means.

For:

```sql
GROUP BY customer_id
```

one output row represents:

```text
one customer
```

For:

```sql
GROUP BY customer_id, month
```

one output row represents:

```text
one customer-month
```

This mental model prevents many bugs.

---

# 9.5 FILTER

PostgreSQL:

```sql
SELECT
    COUNT(*) AS total,
    COUNT(*) FILTER (
        WHERE status = 'completed'
    ) AS completed
FROM orders;
```

This is often cleaner than multiple subqueries.

---

# CHAPTER 10 — WINDOW FUNCTIONS

Window functions are one of the most important advanced SQL concepts.

They allow calculations across related rows **without collapsing those rows into one row per group**.

---

# 10.1 GROUP BY vs Window Function

`GROUP BY`:

```text
many rows
   ↓
one row per group
```

Window function:

```text
many rows
   ↓
same rows + calculated information
```

This distinction is critical.

---

# 10.2 ROW_NUMBER

```sql
SELECT
    customer_id,
    order_id,
    amount,
    ROW_NUMBER() OVER (
        PARTITION BY customer_id
        ORDER BY amount DESC
    ) AS order_rank
FROM orders;
```

Meaning:

> Rank each customer's orders from highest amount to lowest.

---

# 10.3 PARTITION BY

```text
PARTITION BY customer_id
```

means:

> Perform the window calculation independently for each customer.

---

# 10.4 RANK

```sql
RANK() OVER (
    ORDER BY amount DESC
)
```

Ties receive the same rank, with gaps afterward.

---

# 10.5 DENSE_RANK

```sql
DENSE_RANK() OVER (
    ORDER BY amount DESC
)
```

Ties receive the same rank without gaps.

---

# CHAPTER 11 — RANKING, RUNNING TOTALS & ANALYTICS

Window functions become extremely powerful for analytics.

---

# 11.1 Top Order Per Customer

```sql
WITH ranked_orders AS (
    SELECT
        customer_id,
        order_id,
        amount,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY amount DESC
        ) AS rn
    FROM orders
)
SELECT *
FROM ranked_orders
WHERE rn = 1;
```

---

# 11.2 Running Total

```sql
SELECT
    created_at,
    amount,
    SUM(amount) OVER (
        ORDER BY created_at
    ) AS running_total
FROM orders;
```

---

# 11.3 Previous Row

`LAG` lets us compare with the previous row.

```sql
SELECT
    created_at,
    amount,
    LAG(amount) OVER (
        ORDER BY created_at
    ) AS previous_amount
FROM orders;
```

---

# 11.4 Next Row

```sql
LEAD(amount) OVER (
    ORDER BY created_at
)
```

Useful for:

* trend analysis
* event sequences
* time-series comparisons

---

# 11.5 FIRST_VALUE / LAST_VALUE

These can identify values relative to a window.

They are useful but require careful understanding of the window frame.

We will practice them rather than memorize them.

---

# 11.6 Window Function Mental Model

```text
Rows
 ↓
Partition
 ↓
Order
 ↓
Window frame
 ↓
Calculation
 ↓
Original rows + calculated result
```

# CHAPTER 12 — NULL, THREE-VALUED LOGIC & EDGE CASES

Complex SQL often fails at the edges.

---

# 12.1 NULL Comparisons

Wrong:

```sql
WHERE phone = NULL
```

Correct:

```sql
WHERE phone IS NULL
```

---

# 12.2 NULL in Aggregates

For example:

```sql
AVG(price)
```

typically ignores NULL values.

This matters when interpreting results.

---

# 12.3 COUNT Differences

```sql
COUNT(*)
```

counts rows.

```sql
COUNT(phone)
```

counts non-NULL phone values.

These are not equivalent.

---

# 12.4 NULL in Arithmetic

Suppose:

```text
price = NULL
```

Then:

```sql
price * 2
```

will produce NULL.

Use:

```sql
COALESCE(price, 0)
```

when that behavior is actually intended.

---

# 12.5 Edge Case Thinking

For every query ask:

```text
What if there are no rows?

What if there are NULLs?

What if there are duplicates?

What if there are ties?

What if a relationship is missing?

What if a value is zero?

What if two timestamps are identical?
```

This is query engineering.

---

# CHAPTER 13 — DATE & TIME QUERY ENGINEERING

Dates are a major source of bugs.

---

# 13.1 Filter by Range

Prefer carefully defined ranges.

For example:

```sql
WHERE created_at >= '2026-01-01'
  AND created_at < '2026-02-01'
```

This defines a half-open interval:

```text
[2026-01-01, 2026-02-01)
```

This is often safer than trying to construct the final second of a month.

---

# 13.2 DATE_TRUNC

```sql
SELECT
    DATE_TRUNC('month', created_at) AS month,
    SUM(amount)
FROM orders
GROUP BY DATE_TRUNC('month', created_at);
```

Useful for monthly reporting.

---

# 13.3 Intervals

PostgreSQL supports interval arithmetic.

Conceptually:

```sql
created_at + INTERVAL '7 days'
```

---

# 13.4 Time Zones

A timestamp represents an actual point in time differently from a local wall-clock representation.

Production systems must have a deliberate strategy for:

* storage
* application conversion
* display

Don't treat timezone handling as formatting only.

# CHAPTER 14 — TEXT SEARCH & STRING QUERY PATTERNS

---

# 14.1 LIKE

```sql
SELECT *
FROM users
WHERE name LIKE 'Sri%';
```

---

# 14.2 ILIKE

PostgreSQL:

```sql
SELECT *
FROM users
WHERE name ILIKE '%sri%';
```

Useful for case-insensitive matching.

---

# 14.3 Pattern Matching and Performance

A query such as:

```sql
WHERE name ILIKE '%abc%'
```

may not use a normal B-tree index efficiently.

This becomes a performance consideration.

Later, PostgreSQL offers specialized indexing/search mechanisms.

We will not dive into every text-search extension yet.

---

# 14.4 Full-Text Search

PostgreSQL supports full-text search.

Conceptually:

```text
documents
    ↓
tokenization
    ↓
search representation
    ↓
matching
```

This becomes particularly interesting when connected to AI/RAG later.

# CHAPTER 15 — PAGINATION & RESULT NAVIGATION

Applications rarely return millions of rows.

They paginate.

---

# 15.1 OFFSET Pagination

```sql
SELECT *
FROM products
ORDER BY id
LIMIT 20
OFFSET 40;
```

Simple.

But large offsets can become inefficient because the database may still need to process/skip many rows.

---

# 15.2 Keyset Pagination

Instead of:

```text
page = 10000
```

use a known last key:

```sql
SELECT *
FROM products
WHERE id > 2000
ORDER BY id
LIMIT 20;
```

This is often called:

> Keyset pagination

or:

> Cursor pagination

---

# 15.3 Why This Matters

This becomes important for:

* APIs
* large datasets
* infinite scrolling
* high-volume applications

---

# 15.4 Pagination Requirements

A good pagination design needs:

```text
Stable ordering
+
Cursor/key
+
Limit
```

Avoid ambiguous ordering.

If two rows have the same sort value, add a deterministic tie-breaker such as an ID.

# CHAPTER 16 — QUERY COMPOSITION & READABILITY

A query is code.

Treat it like code.

---

# 16.1 Bad Query

A giant unreadable query:

```text
SELECT ... 300 characters of nested logic ...
```

may technically work but be difficult to maintain.

---

# 16.2 Good Query

Use:

* meaningful aliases
* indentation
* CTEs where helpful
* explicit columns
* clear conditions

Example:

```sql
WITH completed_orders AS (
    SELECT
        customer_id,
        amount
    FROM orders
    WHERE status = 'completed'
)
SELECT
    customer_id,
    SUM(amount) AS total_spent
FROM completed_orders
GROUP BY customer_id
ORDER BY total_spent DESC;
```

---

# 16.3 Naming

Avoid:

```sql
SELECT a.x, b.y
FROM customers a
JOIN orders b ...
```

when meaningful aliases are clearer:

```sql
SELECT
    customer.id,
    order.id
FROM customers AS customer
JOIN orders AS order
    ON order.customer_id = customer.id;
```

Short aliases are fine when they remain understandable:

```text
c
o
oi
p
```

---

# 16.4 Comments

Comment the **why**, not every obvious line.

Bad:

```sql
-- select customer id
SELECT customer_id
```

Better:

```sql
-- Restrict to completed orders because cancelled orders
-- should not contribute to recognized revenue.
```

---

# CHAPTER 17 — COMMON SQL ANTI-PATTERNS

---

# Anti-Pattern 1 — SELECT *

Avoid blindly returning every column.

---

# Anti-Pattern 2 — Missing WHERE

Dangerous:

```sql
UPDATE users
SET status = 'inactive';
```

if you intended to update one user.

---

# Anti-Pattern 3 — Incorrect JOIN

Joining on the wrong column can silently produce incorrect data.

---

# Anti-Pattern 4 — Accidental Cartesian Product

Forgetting a join condition can create enormous row combinations.

---

# Anti-Pattern 5 — Aggregating After Row Multiplication

This can inflate counts and sums.

---

# Anti-Pattern 6 — OFFSET at Huge Scale

Simple but potentially inefficient.

---

# Anti-Pattern 7 — Functions Preventing Efficient Filtering

For example:

```sql
WHERE LOWER(email) = 'user@example.com'
```

may interact differently with indexes than a properly designed normalized/search strategy.

Don't optimize blindly; inspect the plan.

---

# Anti-Pattern 8 — N+1 Queries

Application does:

```text
1 query → get customers
100 queries → get each customer's orders
```

Total:

```text
101 queries
```

Sometimes a properly designed join or batch query can solve this more efficiently.

---

# Anti-Pattern 9 — Using SQL to Hide Bad Schema Design

Sometimes the query is impossibly complicated because the underlying data model is poor.

The correct solution may be schema redesign.

---

# CHAPTER 18 — QUERY CORRECTNESS & TESTING

A query should be tested like application code.

---

# 18.1 Test Expected Results

Suppose:

```text
Expected:
5 customers
```

Verify the result.

---

# 18.2 Edge Cases

Test:

* zero rows
* one row
* duplicate values
* NULL
* ties
* missing relationships
* large values
* negative values where relevant

---

# 18.3 Invariants

An invariant is a condition that should remain true.

Example:

```text
order total = sum(order items)
```

Another:

```text
stock >= 0
```

Use these to validate queries and database behavior.

---

# 18.4 Query Regression Tests

If an important query changes:

```text
Old query
 ↓
expected result
```

Compare against:

```text
New query
 ↓
expected result
```

This becomes important in production systems.

# CHAPTER 19 — EXPLAIN & QUERY PLANS

Now we start understanding what PostgreSQL does with a query.

---

# 19.1 EXPLAIN

Example:

```sql
EXPLAIN
SELECT *
FROM products
WHERE price > 1000;
```

PostgreSQL returns a query plan.

---

# 19.2 EXPLAIN ANALYZE

```sql
EXPLAIN ANALYZE
SELECT *
FROM products
WHERE price > 1000;
```

This actually executes the query and reports runtime information.

Be careful when using it with:

```text
INSERT
UPDATE
DELETE
```

because those operations actually execute.

---

# 19.3 What Is a Query Plan?

The planner decides how to execute the query.

Conceptually:

```text
SQL
 ↓
Parser
 ↓
Planner / Optimizer
 ↓
Execution Plan
 ↓
Executor
 ↓
Result
```

---

# 19.4 Scan

You may encounter:

```text
Sequential Scan
Index Scan
Index Only Scan
Bitmap Scan
```

We don't need to memorize every detail yet.

Understand the basic idea:

> PostgreSQL chooses a way to find the required rows.

---

# 19.5 Cost

EXPLAIN includes estimated costs.

These are planner estimates, not directly measured milliseconds.

Don't interpret:

```text
cost=100
```

as:

```text
100 milliseconds
```

---

# 19.6 Actual Time

With:

```sql
EXPLAIN ANALYZE
```

you can see actual execution timing.

Compare:

```text
estimated rows
vs
actual rows
```

This becomes important for diagnosing poor plans.

# CHAPTER 20 — QUERY PERFORMANCE FUNDAMENTALS

Performance isn't just:

> "Make SQL faster."

It is:

```text
Reduce unnecessary work
```

---

# 20.1 Ask Where the Work Happens

Possible problems:

```text
Too many rows scanned
Too many joins
Poor filtering
Bad indexes
Large sorts
Large aggregations
Network transfer
Application-side processing
```

---

# 20.2 Measure Before Optimizing

Never say:

> "This query is slow because it doesn't use an index."

without measuring.

Use:

```text
EXPLAIN
EXPLAIN ANALYZE
```

and actual workload information.

---

# 20.3 Select Only What You Need

Instead of:

```sql
SELECT *
```

use:

```sql
SELECT id, name, price
```

when those are the only required fields.

Benefits can include:

* less data transfer
* less memory
* clearer API boundaries

---

# 20.4 Filter Early

When logically appropriate, reduce the dataset before expensive operations.

---

# 20.5 Avoid Unnecessary Work

For example, don't calculate:

```text
10 million rows
```

when the application needs:

```text
10 rows
```

---

# CHAPTER 21 — INDEX-AWARE QUERY ENGINEERING

V01 introduced indexes.

V02 used them conceptually.

Now we connect indexes with query patterns.

---

# 21.1 Index Exists for Access Patterns

Suppose:

```sql
SELECT *
FROM users
WHERE email = 'user@example.com';
```

If email is frequently searched, an index may help.

---

# 21.2 Composite Index

Suppose queries often use:

```text
customer_id
created_at
```

A composite index can sometimes support such access patterns.

The order of columns matters.

---

# 21.3 Don't Guess

Don't automatically create:

```text
index on every column
```

Instead:

```text
Observe query pattern
       ↓
Measure
       ↓
Design index
       ↓
EXPLAIN
       ↓
Verify
```

---

# 21.4 Selectivity

Indexes are generally more useful when they can significantly narrow the candidate rows.

A column where almost every row has the same value may not be as useful for certain queries.

Again:

> Let actual workload and query plans guide decisions.

---

# 21.5 Write Cost

Indexes must also be maintained when data changes.

Therefore:

```text
More indexes
    ↓
Potentially faster reads
    +
Potentially more write/storage overhead
```

This is an engineering tradeoff.

# CHAPTER 24 — SQL SECURITY & SAFE QUERY CONSTRUCTION

SQL injection remains one of the most important database security concepts.

---

# 24.1 Unsafe

Never construct SQL like:

```text
"SELECT * FROM users WHERE email = '" + email + "'"
```

User input can alter the query.

---

# 24.2 Parameterized

Conceptually:

```text
SQL:
SELECT *
FROM users
WHERE email = $1

Parameter:
user@example.com
```

The database/driver treats the value as data rather than executable SQL syntax.

---

# 24.3 ORM Safety

ORMs often provide parameterization automatically.

But developers can still create unsafe raw SQL.

Therefore:

> ORM does not eliminate security responsibility.

---

# 24.4 Least Privilege

The application database user should not have unnecessary permissions.

This reduces the potential damage if credentials are compromised.

---

# 24.5 Sensitive Data

Avoid returning unnecessary sensitive columns from queries.

Example:

```text
SELECT *
```

could accidentally expose:

* password hashes
* internal tokens
* private metadata
* administrative information

Explicit column selection is often safer.
