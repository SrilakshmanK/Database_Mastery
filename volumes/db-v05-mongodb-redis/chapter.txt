# CHAPTER 01 — WHY NOSQL EXISTS

First, understand the problem.

SQL databases are extremely powerful.

So why did databases like MongoDB and Redis become popular?

Not because relational databases became useless.

Different workloads create different requirements.

---

# 1.1 Relational Strengths

PostgreSQL is excellent when you need:

```text
Strong relationships
Structured data
Constraints
Transactions
Complex queries
Reporting
Consistency
```

For example:

```text
Banking
Orders
Payments
Accounting
Inventory
```

---

# 1.2 Document Database Strengths

Some applications work naturally with documents.

Example:

```json
{
  "name": "Product A",
  "price": 1200,
  "tags": ["electronics", "mobile"],
  "specifications": {
    "ram": "8GB",
    "storage": "256GB"
  }
}
```

This structure can map naturally to application objects.

---

# 1.3 Key-Value Systems

Some requirements are simply:

> Give me this value extremely quickly.

Example:

```text
session:user:123
        ↓
session data
```

Redis is designed for this kind of workload.

---

# 1.4 The Important Lesson

NoSQL does not mean:

> "SQL databases are outdated."

It means:

> **Different data models solve different problems.**

---

# CHAPTER 02 — DATABASE MODEL COMPARISON

Let's establish the major models.

---

# 2.1 Relational

Example:

```text
customers
orders
products
```

Data is organized into related tables.

Best suited for many structured transactional workloads.

---

# 2.2 Document

Example:

```json
{
  "_id": "123",
  "name": "Sri",
  "skills": [
    "JavaScript",
    "React",
    "Node.js"
  ]
}
```

MongoDB stores documents in collections.

---

# 2.3 Key-Value

Conceptually:

```text
key
 ↓
value
```

Example:

```text
user:123:session
       ↓
session information
```

Redis is commonly used this way.

---

# 2.4 Search Systems

Search engines optimize for:

```text
Text search
Ranking
Filtering
Aggregations
```

These are not automatically replacements for PostgreSQL.

---

# 2.5 Vector Databases

Vector databases optimize for:

```text
Embedding
Similarity
Nearest-neighbor retrieval
```

We will connect this to AI in DB V06.

---

# 2.6 Database Selection

The correct question is:

```text
What data?
What consistency?
What access pattern?
What scale?
What latency?
What operational complexity?
```

Not:

> "Which database is trending?"

# CHAPTER 03 — MONGODB MENTAL MODEL

MongoDB is a document-oriented database.

The hierarchy is approximately:

```text
MongoDB Server
      ↓
Database
      ↓
Collection
      ↓
Document
      ↓
Field
```

Compare with PostgreSQL:

```text
PostgreSQL Server
      ↓
Database
      ↓
Schema
      ↓
Table
      ↓
Row
      ↓
Column
```

---

# 3.1 Collection

MongoDB's collection is roughly analogous to a relational table.

But it is not identical.

A collection contains documents.

---

# 3.2 Document

Example:

```json
{
  "_id": "user123",
  "name": "Sri",
  "email": "sri@example.com",
  "skills": [
    "Node.js",
    "React",
    "MongoDB"
  ]
}
```

A document can contain:

* strings
* numbers
* booleans
* arrays
* nested objects
* dates
* ObjectIds
* other BSON types

---

# 3.3 Flexible Schema

MongoDB allows documents in the same collection to have different structures.

For example:

```json
{
  "name": "User A",
  "age": 22
}
```

and:

```json
{
  "name": "User B",
  "age": 25,
  "skills": ["Python"]
}
```

can exist in the same collection.

But:

> Flexible schema does not mean no schema.

Your application still has a data model.

---

# 3.4 Schema-on-Read vs Schema-on-Write

Relational systems commonly enforce more structure through schema definitions.

MongoDB can allow more flexibility.

But uncontrolled flexibility can produce:

```text
Document A
field = email

Document B
field = emailAddress

Document C
field = mail
```

This becomes a maintenance nightmare.

Therefore:

> Flexible schema requires disciplined application design.

---

# CHAPTER 04 — DOCUMENTS, BSON & COLLECTIONS

MongoDB stores documents using BSON.

BSON means:

> Binary JSON.

It extends JSON with additional types and binary representation.

---

# 4.1 Example

```json
{
  "_id": ObjectId("..."),
  "name": "Product A",
  "price": 1500,
  "active": true,
  "createdAt": ISODate("2026-01-01")
}
```

---

# 4.2 ObjectId

MongoDB commonly uses:

```text
ObjectId
```

as the default `_id`.

It is designed to provide a unique identifier.

You don't need to memorize its internal bit layout.

Understand:

> `_id` uniquely identifies a document within the collection.

---

# 4.3 Arrays

Documents can naturally contain arrays:

```json
{
  "name": "Sri",
  "skills": [
    "Node.js",
    "React",
    "PostgreSQL"
  ]
}
```

This is one of the major differences from normalized relational modeling.

---

# 4.4 Nested Documents

```json
{
  "name": "Sri",
  "address": {
    "city": "Coimbatore",
    "country": "India"
  }
}
```

This is useful when the nested data belongs naturally to the parent document.

# CHAPTER 08 — MONGODB DATA MODELING

This is the most important MongoDB chapter.

Don't start with:

> "How do I convert my PostgreSQL tables into MongoDB collections?"

Start with:

> **How will the application use the data?**

---

# 8.1 Relational Thinking

PostgreSQL often encourages:

```text
Normalize
Separate entities
Join when needed
```

MongoDB often encourages:

```text
Model around access patterns
Embed data that belongs together
Reference data that should remain independent
```

---

# 8.2 Example

Suppose:

```text
user
addresses
```

If a user usually reads their address together with their profile, embedding may make sense:

```json
{
  "_id": 1,
  "name": "Sri",
  "address": {
    "city": "Coimbatore",
    "country": "India"
  }
}
```

---

# 8.3 Data Modeling Question

Ask:

```text
How often is this data read?
How often is it updated?
How large can it become?
Does it belong to one parent?
Does it have an independent lifecycle?
```

These questions drive the model.

---

# CHAPTER 09 — EMBEDDING VS REFERENCING

This is one of the most important MongoDB decisions.

---

# 9.1 Embedding

Example:

```json
{
  "_id": 1,
  "name": "Sri",
  "addresses": [
    {
      "city": "Coimbatore"
    }
  ]
}
```

Advantages:

```text
Single document read
Natural object structure
Often fewer queries
```

---

# 9.2 Referencing

Instead:

```json
{
  "_id": 1,
  "name": "Sri",
  "addressId": 500
}
```

and:

```json
{
  "_id": 500,
  "city": "Coimbatore"
}
```

This is useful when the referenced data has its own lifecycle or is shared.

---

# 9.3 One-to-Few

Embedding is often appropriate when:

```text
one user
→ few addresses
```

---

# 9.4 One-to-Many

Consider:

```text
one customer
→ thousands of orders
```

Embedding all orders inside the customer document can become problematic.

Referencing orders as separate documents may be more appropriate.

---

# 9.5 Unbounded Arrays

Avoid designs where an array can grow without a practical limit.

For example:

```json
{
  "user": "123",
  "allEvents": [
    ...
  ]
}
```

If millions of events accumulate, the document becomes problematic.

---

# 9.6 Rule

A useful starting principle:

> Embed data that is naturally owned and commonly read with the parent.

> Reference data that has an independent lifecycle, is shared, or can grow without bound.

These are guidelines, not absolute rules.

---

# CHAPTER 10 — SCHEMA VALIDATION & DATA INTEGRITY

Flexible schema does not mean careless schema.

---

# 10.1 Validation

MongoDB can enforce document validation rules.

For example:

```text
email must exist
age must be a number
status must be one of allowed values
```

---

# 10.2 Application Validation

Backend frameworks can also validate data.

For example:

```text
FastAPI
Pydantic
```

or:

```text
Node.js
Zod
Mongoose
```

But validation should be designed carefully across the application/database boundary.

---

# 10.3 Why Database Validation Matters

Imagine two backend services writing to the same collection.

If only one service validates:

```text
Service A
✓ valid data

Service B
✗ malformed data
```

Database-level validation provides another layer of protection.

---

# 10.4 Defense in Depth

Use:

```text
API validation
+
application validation
+
database validation
```

where appropriate.

# CHAPTER 11 — MONGODB INDEXES

MongoDB indexes serve the same fundamental purpose as PostgreSQL indexes:

> Reduce unnecessary work for supported access patterns.

---

# 11.1 Basic Index

Example:

```javascript
db.users.createIndex({
  email: 1
});
```

---

# 11.2 Query

```javascript
db.users.find({
  email: "sri@example.com"
});
```

The index can support efficient lookup.

---

# 11.3 Compound Index

Example:

```javascript
db.orders.createIndex({
  customerId: 1,
  createdAt: -1
});
```

This can support queries involving both fields.

---

# 11.4 Index Order

The order of fields in a compound index matters.

Think:

```text
(customerId, createdAt)
```

as an ordered access path.

You should design indexes from actual query patterns.

---

# 11.5 Explain

MongoDB provides query explanation tools.

Conceptually:

```javascript
db.orders.find({
  customerId: 123
}).explain("executionStats");
```

Inspect:

```text
documents examined
documents returned
index usage
execution statistics
```

---

# 11.6 Index Cost

Just like PostgreSQL:

```text
Index
 ↓
faster reads
+
storage
+
write/update overhead
```

Don't index everything.

# CHAPTER 12 — MONGODB AGGREGATION PIPELINE

MongoDB's aggregation pipeline is one of its most powerful features.

---

# 12.1 Mental Model

Think:

```text
Documents
   ↓
Stage 1
   ↓
Stage 2
   ↓
Stage 3
   ↓
Result
```

---

# 12.2 `$match`

Filter documents:

```javascript
{
  $match: {
    status: "completed"
  }
}
```

---

# 12.3 `$group`

Group documents:

```javascript
{
  $group: {
    _id: "$customerId",
    totalSpent: {
      $sum: "$amount"
    }
  }
}
```

---

# 12.4 `$sort`

```javascript
{
  $sort: {
    totalSpent: -1
  }
}
```

---

# 12.5 `$limit`

```javascript
{
  $limit: 10
}
```

---

# 12.6 Pipeline Example

```javascript
db.orders.aggregate([
  {
    $match: {
      status: "completed"
    }
  },
  {
    $group: {
      _id: "$customerId",
      totalSpent: {
        $sum: "$amount"
      }
    }
  },
  {
    $sort: {
      totalSpent: -1
    }
  },
  {
    $limit: 10
  }
]);
```

Mental model:

```text
completed orders
      ↓
customer totals
      ↓
sort
      ↓
top 10
```

Very similar to the SQL reasoning developed in V03.

---

# 12.7 `$project`

Transform output fields.

---

# 12.8 `$unwind`

Convert array elements into separate pipeline documents.

Example:

```text
Document
  skills: [A, B, C]
```

becomes conceptually:

```text
Document + A
Document + B
Document + C
```

---

# 12.9 `$lookup`

MongoDB can perform join-like operations.

But don't automatically design MongoDB like a relational database.

If you frequently need complicated joins, reconsider whether the document model matches the access pattern.

# CHAPTER 13 — MONGODB TRANSACTIONS & CONSISTENCY

MongoDB supports transactions.

This is important because an old misconception is:

> "NoSQL means no transactions."

That's incorrect.

---

# 13.1 Single-Document Atomicity

MongoDB operations on a single document have strong atomicity guarantees.

This is one reason document modeling is important.

If related information can safely live inside one document, you may avoid cross-document transaction complexity.

---

# 13.2 Multi-Document Transactions

MongoDB supports transactions spanning multiple documents/collections under supported deployment configurations.

Conceptually:

```text
BEGIN
 ↓
operation 1
 ↓
operation 2
 ↓
COMMIT
```

or:

```text
ROLLBACK
```

---

# 13.3 Important Design Principle

Transactions are useful.

But don't use transactions to compensate for a poor data model.

Ask first:

> Can the data model make the operation naturally atomic?

---

# 13.4 Consistency Trade-Off

Database architecture involves trade-offs between:

```text
Consistency
Availability
Latency
Scalability
Complexity
```

You need to understand the requirements before choosing a design.

# CHAPTER 16 — REDIS MENTAL MODEL

Now we move to Redis.

Redis is an in-memory data store commonly used for:

* caching
* sessions
* counters
* rate limiting
* queues
* temporary state
* distributed coordination patterns

---

# 16.1 Core Model

Redis is fundamentally:

```text
KEY
 ↓
VALUE
```

Example:

```text
user:123:profile
       ↓
serialized data
```

---

# 16.2 In-Memory

Redis is designed for very fast access using memory.

This is a major reason it is useful as a cache and fast state store.

---

# 16.3 Redis Is Not Automatically Your Primary Database

A common architecture is:

```text
Application
   │
   ├── Redis
   │
   └── PostgreSQL
```

Redis may contain derived or temporary data.

PostgreSQL may remain the durable source of truth.

---

# CHAPTER 18 — REDIS EXPIRATION & TTL

One of Redis's most important features is expiration.

---

# 18.1 TTL

Example:

```text
session:abc
TTL = 3600 seconds
```

After the expiration period, Redis can remove the key.

---

# 18.2 Why TTL Matters

Useful for:

```text
Caches
OTP-like temporary state
Sessions
Temporary locks
Rate-limit windows
Short-lived tokens
```

---

# 18.3 Key Expiration

Conceptually:

```text
SET cache:user:123 data
EXPIRE cache:user:123 300
```

The data is intended to live temporarily.

---

# 18.4 TTL Is Not Business Logic

Don't rely on Redis expiration alone for permanent business records.

For example:

```text
payment
order
invoice
```

should not disappear simply because a TTL expired.

# CHAPTER 19 — REDIS CACHING

Caching is one of the most important practical uses of Redis.

---

# 19.1 Why Cache?

Suppose:

```text
API
 ↓
PostgreSQL
 ↓
Expensive query
```

If the same result is requested thousands of times:

```text
1000 requests
→ 1000 database queries
```

A cache may reduce the database workload.

---

# 19.2 Cache-Aside Pattern

This is one of the most common patterns.

```text
Request
   ↓
Check Redis
   │
   ├── HIT → return data
   │
   └── MISS
          ↓
      PostgreSQL
          ↓
      Store in Redis
          ↓
       Return
```

---

# 19.3 Example

Request:

```text
GET /products/123
```

Application:

```text
Redis key:
product:123
```

If found:

```text
return cached result
```

Otherwise:

```text
PostgreSQL
 ↓
Redis
 ↓
Response
```

---

# 19.4 Cache Key Design

Good:

```text
product:123
user:456:profile
```

Bad:

```text
data1
x
temp
```

Keys should be predictable and meaningful.

---

# 19.5 TTL Selection

TTL depends on:

```text
How often data changes
How stale it can be
How expensive the source query is
How much cache storage is available
```

There is no universal TTL.

# CHAPTER 21 — CACHE INVALIDATION & FAILURE MODES

Caching is easy to add.

Correct caching is difficult.

---

# 21.1 The Classic Problem

PostgreSQL:

```text
price = 1000
```

Redis:

```text
price = 1000
```

Application updates PostgreSQL:

```text
price = 1200
```

Redis still contains:

```text
1000
```

Now users receive stale data.

---

# 21.2 Cache Invalidation

After updating the source:

```text
Update PostgreSQL
       ↓
Invalidate Redis key
```

For example:

```text
product:123
```

---

# 21.3 Update vs Delete

Common strategy:

```text
Database update
      ↓
Delete cache
```

Next request:

```text
Cache miss
      ↓
Database
      ↓
Fresh cache
```

This is often simpler than trying to update every cached representation correctly.

---

# 21.4 Cache Stampede

Suppose a popular cache expires:

```text
product:123
```

1000 requests arrive simultaneously.

All miss cache:

```text
1000 requests
     ↓
1000 DB queries
```

This can overload the database.

---

# 21.5 Possible Mitigations

Depending on requirements:

* jittered TTLs
* request coalescing
* locks
* stale-while-revalidate
* prewarming
* controlled refresh

Don't blindly add distributed locks everywhere.

---

# 21.6 Cache Failure

What happens if Redis is down?

A good architecture should define this.

Possibility:

```text
Redis down
   ↓
Fallback to PostgreSQL
```

if the cache is optional.

But if Redis stores essential session state:

```text
Redis down
   ↓
authentication/session impact
```

Therefore:

> Redis's role must be explicitly defined.

---

# CHAPTER 22 — REDIS RELIABILITY FUNDAMENTALS

Redis can persist data depending on its configuration and deployment model.

But you should understand the difference between:

```text
Cache
```

and:

```text
Durable datastore
```

---

# 22.1 Cache Role

If Redis contains:

```text
derived data
```

then losing it may be acceptable.

The application can rebuild it from PostgreSQL.

---

# 22.2 State Role

If Redis contains:

```text

```

then availability and persistence requirements become more important.

---

# 22.3 Persistence Options

Redis provides persistence mechanisms such as:

```text

AOF
```

Understand them conceptually.

---

# 22.4 High Availability

Redis can be deployed with replication and other availability mechanisms.

But complexity increases.

The correct question remains:

> What business role does Redis have?

# CHAPTER 24 — POLYGLOT PERSISTENCE

Using different databases for different requirements is called:

> Polyglot persistence.

---

# 24.1 Example

```text
PostgreSQL
→ orders

MongoDB
→ flexible content

Redis
→ cache
```

---

# 24.2 Why Use It?

Because different workloads have different requirements.

---

# 24.3 The Cost

Now your architecture contains:

```text
3 databases
```

instead of:

```text
1 database
```

You now have:

```text
3 authentication systems
3 monitoring surfaces
3 backup strategies
3 failure modes
3 upgrade paths
```

Therefore:

> Don't introduce a second database without a clear reason.

---

# 24.4 Source of Truth

This concept is critical.

For example:

```text
PostgreSQL
   ↓
Source of truth
```

Redis:

```text
Derived cache
```

If Redis disappears:

```text
Rebuild from PostgreSQL
```

This creates a much safer architecture.

---

# 24.5 Data Ownership

For each piece of data define:

```text
Who owns it?
Where is the source of truth?
Where are copies stored?
How are copies updated?
What happens if the copy disappears?
```

This is database architecture.
