# CHAPTER 01 — POSTGRESQL MENTAL MODEL

## 1.1 What Is PostgreSQL?

PostgreSQL is an open-source relational database management system.

It provides:

* data storage
* SQL
* transactions
* concurrency control
* constraints
* indexes
* security
* recovery
* extensibility

But remember:

> PostgreSQL is not SQL.

SQL is a language.

PostgreSQL is a database system that implements SQL and provides many additional capabilities.

---

# 1.2 SQL vs PostgreSQL

Think:

```text
SQL
 ↓
Language / rules for communicating with relational databases

PostgreSQL
 ↓
Actual database system implementing SQL
```

Similar idea:

```text
HTTP
 ↓
Protocol

Web server
 ↓
Software implementing HTTP
```

The distinction matters.

---

# 1.3 PostgreSQL in Your Backend

Your future architecture may look like:

```text
React
   ↓
FastAPI
   ↓
PostgreSQL
```

or:

```text
React
   ↓
Node.js / Express
   ↓
PostgreSQL
```

PostgreSQL becomes the persistent data layer.

# CHAPTER 06 — CREATING TABLES

Now we start writing SQL.

---

# 6.1 Basic Table

```sql
CREATE TABLE users (
    id INTEGER,
    name TEXT,
    email TEXT
);
```

This creates:

```text
users
├── id
├── name
└── email
```

---

# 6.2 Primary Key

Better:

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    name TEXT,
    email TEXT
);
```

Now `id` uniquely identifies each row.

---

# 6.3 Generated IDs

PostgreSQL supports identity columns.

Example:

```sql
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT NOT NULL
);
```

This allows PostgreSQL to generate identifiers automatically.

---

# 6.4 Create Related Tables

```sql
CREATE TABLE customers (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT UNIQUE NOT NULL
);
```

Then:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    created_at TIMESTAMP NOT NULL,
    FOREIGN KEY (customer_id)
        REFERENCES customers(id)
);
```

Now the relationship exists in the database.


# 7.5 Date and Time

Important types:


# 7.6 UUID


# CHAPTER 08 — CONSTRAINTS

---

# 8.1 NOT NULL

```sql

```

The column cannot be NULL.

---

# 8.2 UNIQUE

```sql

```

Duplicate emails are rejected.

---

# 8.3 CHECK

```sql

    CHECK (price >= 0)
```

---

# 8.4 DEFAULT

```sql

```

---

# 8.5 FOREIGN KEY

```sql
customer_id BIGINT
REFERENCES customers(id)
```

---

# 8.6 Combined Example

```sql
CREATE TABLE products (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    price NUMERIC(10,2) NOT NULL CHECK (price >= 0),
    stock INTEGER NOT NULL DEFAULT 0 CHECK (stock >= 0),
    sku TEXT UNIQUE NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

This is much stronger than:

```sql
CREATE TABLE products (
    id INTEGER,
    name TEXT,
    price TEXT,
    stock TEXT
);
```

# CHAPTER 12 — NULL & THREE-VALUED LOGIC

NULL requires special care.

---

# 12.1 Incorrect

Don't write:

```sql
WHERE phone = NULL
```

Use:

```sql
WHERE phone IS NULL
```

---

# 12.2 NOT NULL

```sql
WHERE phone IS NOT NULL
```

---

# 12.3 Why?

SQL logic isn't simply:

```text
TRUE
FALSE
```

With NULL, we can get:

```text
TRUE
FALSE
UNKNOWN
```

This is called three-valued logic.

---

# 12.4 Example

Suppose:

```text
price = NULL
```

Then:

```sql
price > 1000
```

doesn't become TRUE or FALSE in the ordinary sense.

It evaluates to UNKNOWN.

This affects filtering and conditions.

# CHAPTER 13 — UPDATE & DELETE

## 13.1 UPDATE

```sql
UPDATE products
SET price = 1600
WHERE id = 1;
```

---

# 13.2 Multiple Columns

```sql
UPDATE products
SET
    price = 1600,
    stock = 25
WHERE id = 1;
```

---

# 13.3 Critical Safety Rule

Never casually run:

```sql
UPDATE products
SET price = 1600;
```

unless you intentionally want to update every row.

Always understand the `WHERE` condition.

---

# 13.4 DELETE

```sql

WHERE id = 1;
```

Again:

```sql
DELETE FROM products;
```

deletes every row.

---

# 13.5 Soft Delete

Many production systems avoid immediately deleting important records.

Instead:

```text
deleted_at
```

or:

```text
is_deleted
```

can be used.

But soft deletion has tradeoffs and should not be added blindly.

We will discuss this through application design later.

# CHAPTER 15 — GROUP BY & HAVING

Suppose:

```text
orders
```

contains:

```text
customer_id
amount
```

We can calculate total spending per customer.

```sql
SELECT
    customer_id,
    SUM(amount) AS total_spent
FROM orders
GROUP BY customer_id;
```

---

# 15.1 HAVING

`WHERE` filters rows.

`HAVING` filters groups.

Example:

```sql
SELECT
    customer_id,
    SUM(amount) AS total_spent
FROM orders
GROUP BY customer_id
HAVING SUM(amount) > 10000;
```

Meaning:

> Return customers whose total spending exceeds 10,000.

---

# 15.2 Important Difference

```text
WHERE
→ before grouping

HAVING
→ after grouping
```

This distinction becomes important in V03.

# CHAPTER 16 — JOINS

Joins are fundamental to relational databases.

Suppose:

```text
customers
```

and:

```text
orders
```

---

# 16.1 INNER JOIN

```sql
SELECT
    customers.name,
    orders.id,
    orders.amount
FROM customers
INNER JOIN orders
    ON orders.customer_id = customers.id;
```

This returns matching records.

---

# 16.2 LEFT JOIN

```sql
SELECT
    customers.name,
    orders.id
FROM customers
LEFT JOIN orders
    ON orders.customer_id = customers.id;
```

This keeps every customer, even if they have no order.

---

# 16.3 Why LEFT JOIN Matters

Suppose we want:

> Find all customers, including customers who never ordered anything.

`INNER JOIN` would remove customers without orders.

`LEFT JOIN` preserves them.

---

# 16.4 RIGHT JOIN

Exists, but generally less common in everyday application SQL because many queries can be expressed more clearly using `LEFT JOIN`.

We need to understand it, not prioritize it.

---

# 16.5 FULL OUTER JOIN

Returns unmatched rows from both sides.

Useful in certain analytical/data reconciliation situations.

Not something you need to force into every project.

---

# 16.6 CROSS JOIN

Produces combinations between rows.

Potentially enormous.

Use deliberately.

---

# 16.7 Join Mental Model

Always ask:

> What relationship am I trying to combine?

Then:

```text
Which table?
Which key?
Which rows should survive?
```

Don't memorize join diagrams without understanding the business question.

# CHAPTER 19 — POSTGRESQL TRANSACTIONS

Now connect V01's ACID theory to actual PostgreSQL.

---

# 19.1 BEGIN

```sql
BEGIN;
```

---

# 19.2 Operations

```sql
UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;
```

---

# 19.3 COMMIT

```sql
COMMIT;
```

Changes become part of the committed transaction.

---

# 19.4 ROLLBACK

```sql
ROLLBACK;
```

Undo the transaction's changes.

---

# 19.5 Example

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;

COMMIT;
```

The two operations belong to one logical unit.

---

# 19.6 Why Transactions Matter in Backend APIs

Imagine:

```text
POST /transfer
```

A backend endpoint may need multiple database operations.

You don't want:

```text
Operation 1 succeeds
Operation 2 fails
```

and leave the system in an invalid state.

The transaction boundary protects the operation.

# CHAPTER 21 — DATABASE USERS, ROLES & PERMISSIONS

PostgreSQL has a role system.

---

# 21.1 Create a Role

Conceptually:

```sql
CREATE ROLE app_user LOGIN PASSWORD '...';
```

Never use real passwords in source code or documentation.

---

# 21.2 Permissions

Example:

```sql
GRANT SELECT ON products TO app_user;
```

The principle:

> Give only the permissions required.

---

# 21.3 Read-Only Role

A reporting application might need:

```text
SELECT
```

but not:

```text
INSERT
UPDATE
DELETE
```

This is least privilege.

---

# 21.4 Application Database User

Your backend should ideally use a dedicated database role rather than a superuser.

Bad:

```text
Application
   ↓
postgres superuser
```

Better:

```text
Application
   ↓
app_user
   ↓
only required permissions
```

# 22.1 pg_dump

A logical backup can be created using PostgreSQL tools.

Conceptually:

```bash
pg_dump database_name > backup.sql
```

---

# 22.2 Restore

A SQL-format dump can be restored using:

```bash
psql database_name < backup.sql
```

Exact commands depend on authentication, format, and environment.

---

# 22.3 Why Practice This Now?

Because:

> Database engineering isn't only about writing queries.

You must eventually be able to answer:

> "What happens if the database disappears?"

---

# 22.4 Important Rule

Never consider:

```text
backup.sql exists
```

to mean:

```text
recovery works
```

Actually test the restore.

# 23.3 ORM vs SQL

An ORM can allow:

```text
User.find(...)
```

instead of manually writing SQL.

But:

> ORM knowledge does not replace SQL knowledge.

You should understand what query the ORM is ultimately causing the database to execute.

This becomes extremely important in DB V03.

---

# 23.4 Parameterized Queries

Never build SQL by concatenating untrusted user input.

Bad:

```text
"SELECT * FROM users WHERE email = '" + email + "'"
```

Use parameterized queries.

Conceptually:

```text
SQL template
     +
parameters
     ↓
database
```

This protects against SQL injection.
