# CHAPTER 01 — POSTGRESQL ARCHITECTURE MENTAL MODEL

Before learning individual components, understand the whole system.

PostgreSQL is not simply:

```text
database = files
```

It is a running server system.

Conceptually:

```text
                    PostgreSQL
                        │
             ┌──────────┴──────────┐
             │                     │
        Client Layer          Server Layer
             │                     │
       Application             Processes
             │                     │
         Driver                Planner
             │                 Executor
         Connection             Cache
             │                 Storage
             └──────────────┬──────┘
                            │
                           Disk
```

---

# 1.1 PostgreSQL Server

The PostgreSQL server manages:

* connections
* SQL execution
* transactions
* memory
* storage
* indexes
* WAL
* locks
* background processes
* recovery

---

# 1.2 Database

A PostgreSQL server can contain multiple databases.

```text
PostgreSQL Server
│
├── database_a
├── database_b
└── database_c
```

Within a database:

```text
database
   ↓
schemas
   ↓
tables
   ↓
rows
```

---

# 1.3 Why This Matters

When debugging:

> "My database is slow"

is too vague.

You need to ask:

```text
Connection problem?
Query problem?
Lock problem?
CPU problem?
Memory problem?
Storage problem?
WAL problem?
Vacuum problem?
Network problem?
Application problem?
```

This is systems thinking applied to databases.

# CHAPTER 02 — POSTGRESQL PROCESSES, CONNECTIONS & SESSIONS

One of the first production concepts is:

> A database connection is not free.

---

# 2.1 Application Connection

Your backend might do:

```text
Node.js / FastAPI
      ↓
PostgreSQL Driver
      ↓
TCP connection
      ↓
PostgreSQL
```

A connection represents a communication channel between application and database.

---

# 2.2 Connection Explosion

Imagine:

```text
100 application instances
×
20 database connections
=
2000 connections
```

That can become a serious problem.

The database has finite resources.

---

# 2.3 Connection Pool

Instead:

```text
Application
     ↓
Connection Pool
 ┌───┼───┐
 C1  C2  C3
 └───┼───┘
     ↓
 PostgreSQL
```

The application reuses connections.

---

# 2.4 Check Connections

PostgreSQL provides:

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state
FROM pg_stat_activity;
```

You can inspect active sessions.

---

# 2.5 Idle vs Active

A connection can be:

```text
active
idle
idle in transaction
```

`idle in transaction` deserves attention because an open transaction can hold resources or prevent cleanup.

---

# 2.6 Production Lesson

Connection management belongs to:

```text
Application Engineering
+
Database Engineering
```

It is not purely a database problem.

Sequential Scan

# CHAPTER 04 — MEMORY, SHARED BUFFERS & CACHING

Databases would be painfully slow if every operation required reading from disk.

Memory is therefore extremely important.

---

# 4.1 Basic Storage Hierarchy

Conceptually:

```text
CPU Cache
   ↓
RAM
   ↓
SSD
   ↓
Network / Remote Storage
```

Generally:

```text
faster
↑
CPU cache
RAM
SSD
network storage
↓
slower
```

---

# 4.2 PostgreSQL Shared Buffers

PostgreSQL maintains shared memory for database pages.

Conceptually:

```text
Disk
 ↓
Database Page
 ↓
Shared Buffer
 ↓
Query
```

If required data is already in memory, PostgreSQL can avoid reading it from disk.

---

# 4.3 Cache Hit

Suppose a query repeatedly accesses the same data.

First request:

```text
Disk → Memory
```

Later:

```text
Memory → Query
```

This can dramatically improve performance.

---

# 4.4 OS Cache

PostgreSQL also interacts with the operating system's filesystem cache.

Therefore the complete memory picture isn't simply:

```text
PostgreSQL memory
```

It involves:

```text
PostgreSQL memory
+
Operating system cache
+
Storage cache
```

---

# 4.5 Practical Lesson

Don't blindly increase memory parameters.

Memory tuning requires understanding:

* workload
* available RAM
* PostgreSQL configuration
* OS behavior
* concurrency

---

# CHAPTER 05 — POSTGRESQL STORAGE ARCHITECTURE

PostgreSQL stores persistent database information on disk.

At a high level:

```text
PostgreSQL data directory
│
├── databases
├── tables
├── indexes
├── WAL
├── configuration
└── system metadata
```

The exact internal directory structure should not be manipulated manually.

Use PostgreSQL tools.

---

# 5.1 Data Directory

You can find the active data directory using PostgreSQL configuration/tools rather than guessing filesystem paths.

For example:

```sql
SHOW data_directory;
```

---

# 5.2 Tables Are Stored

A table isn't just an abstract SQL object.

Eventually:

```text
SQL table
    ↓
physical storage
    ↓
disk pages
```

---

# 5.3 Indexes Also Consume Storage

An index is additional physical data.

Therefore:

```text
Table
+
Indexes
=
Storage
```

More indexes aren't free.

# CHAPTER 06 — PAGES, TUPLES & TABLE STORAGE

This chapter gives you the physical mental model.

---

# 6.1 Page

PostgreSQL organizes storage into fixed-size pages.

A common PostgreSQL page size is:

```text
8 KB
```

Think of a page as a unit of storage I/O.

---

# 6.2 Tuple

A table row is internally represented as a tuple.

Conceptually:

```text
Page
│
├── Tuple
├── Tuple
├── Tuple
└── Tuple
```

---

# 6.3 Why Pages Matter

A database doesn't usually think:

> "Read one row from SSD."

It works with blocks/pages of storage.

Therefore:

```text
More pages read
=
More I/O work
```

---

# 6.4 Wide Rows

If rows become very large, fewer rows fit into each page.

That can increase storage and I/O requirements.

---

# 6.5 TOAST

PostgreSQL has mechanisms for handling values too large to fit conveniently inside normal row storage.

This is known as:

> TOAST — The Oversized-Attribute Storage Technique.

You don't need to memorize its internal implementation.

Understand:

> PostgreSQL has mechanisms for storing large field values separately when necessary.

---

# CHAPTER 07 — MVCC FROM FIRST PRINCIPLES

This is one of the most important PostgreSQL concepts.

MVCC means:

> Multi-Version Concurrency Control.

---

# 7.1 The Problem

Imagine:

```text
Transaction A
reads account balance

Transaction B
updates account balance
```

What should A see?

Databases need rules for consistent visibility.

---

# 7.2 Multiple Versions

PostgreSQL doesn't simply overwrite the conceptual history of a row in place for every update.

Instead, PostgreSQL's MVCC model maintains row-version information that allows transactions to determine which version is visible to them.

Conceptually:

```text
Row version 1
      ↓
Row version 2
      ↓
Row version 3
```

---

# 7.3 Why This Is Powerful

MVCC helps allow:

```text
Reader
+
Writer
```

to operate concurrently without every read blocking every write.

---

# 7.4 The Cost

Old row versions eventually need cleanup.

That leads directly to:

```text
VACUUM
```

---

# 7.5 MVCC Mental Model

Think:

```text
UPDATE
 ↓
new row version
 ↓
old version becomes obsolete
 ↓
VACUUM eventually cleans obsolete versions
```

This is simplified, but it is an extremely useful operational model.

---

# CHAPTER 08 — TRANSACTIONS & ISOLATION LEVELS

A transaction is a logical unit of work.

---

# 8.1 Atomicity

Either:

```text
everything succeeds
```

or:

```text
everything rolls back
```

---

# 8.2 Isolation

Concurrent transactions should behave according to the database's isolation rules.

PostgreSQL supports isolation levels including:

```text
Read Committed
Repeatable Read
Serializable
```

PostgreSQL also accepts the SQL standard name `Read Uncommitted`, but its behavior is effectively the same as Read Committed.

---

# 8.3 Read Committed

This is PostgreSQL's default isolation level.

A statement sees data according to PostgreSQL's read-committed visibility rules.

Important distinction:

> Transaction-level consistency and statement-level visibility are not identical concepts.

---

# 8.4 Repeatable Read

Provides a more stable transaction snapshot.

Useful when multiple statements need a consistent view.

---

# 8.5 Serializable

Attempts to provide behavior equivalent to serial execution of transactions.

But it can result in serialization failures that the application must retry.

---

# 8.6 Practical Backend Example

Suppose you are transferring money:

```text
BEGIN

debit account A

credit account B

COMMIT
```

If credit fails:

```text
ROLLBACK
```

The transfer should not leave the system half-completed.

---

# CHAPTER 09 — LOCKS & CONCURRENCY

Transactions alone don't explain every concurrency problem.

Locks matter.

---

# 9.1 Why Locks Exist

Imagine:

```text
Transaction A
updates product stock

Transaction B
updates the same product stock
```

The database needs coordination.

---

# 9.2 Row-Level Lock

Conceptually:

```text
Transaction A
      ↓
locks row
      ↓
updates
```

Transaction B may need to wait depending on the operation and lock conflict.

---

# 9.3 Table-Level Locks

PostgreSQL also has stronger locks affecting tables.

Different lock modes conflict differently.

You don't need to memorize the complete lock matrix at this stage.

Understand:

> Different operations require different levels of coordination.

---

# 9.4 Deadlock

Classic scenario:

```text
Transaction A
locks Row 1
waits for Row 2

Transaction B
locks Row 2
waits for Row 1
```

Result:

```text
A → waiting
B → waiting
```

PostgreSQL detects deadlocks and aborts one transaction.

---

# 9.5 Avoiding Deadlocks

One important strategy:

> Acquire resources in a consistent order.

For example:

```text
Always lock account A before account B
```

rather than allowing different code paths to lock them in different orders.

---

# 9.6 Inspecting Locks

PostgreSQL provides statistics/views for investigating activity and locks.

One useful starting point is:

```sql
SELECT
    pid,
    usename,
    state,
    query
FROM pg_stat_activity;
```

Later, combine activity information with lock views during troubleshooting.

---

# CHAPTER 10 — WAL & DURABILITY

WAL means:

> Write-Ahead Logging.

This is fundamental to PostgreSQL durability and recovery.

---

# 10.1 Core Principle

Before certain data changes are considered durably committed, PostgreSQL records the necessary change information in the WAL.

Conceptually:

```text
Transaction change
       ↓
WAL
       ↓
durability boundary
       ↓
data pages
```

The exact internals are more sophisticated, but this is the key idea.

---

# 10.2 Why WAL?

Imagine:

```text
Database page in memory
       ↓
server crashes
       ↓
memory lost
```

Without durable change records, recent changes could disappear.

WAL provides the information needed for recovery.

---

# 10.3 WAL Enables

WAL is fundamental to:

* crash recovery
* replication
* point-in-time recovery
* durability

---

# 10.4 Important Mental Model

Do not think:

> "PostgreSQL writes every changed row directly to disk and that's it."

Think:

```text
Change
 ↓
WAL
 ↓
durability
 ↓
data pages eventually persisted
```

---

# CHAPTER 11 — CHECKPOINTS & CRASH RECOVERY

---

# 11.1 Checkpoint

A checkpoint establishes a known recovery point where dirty database pages are written toward persistent storage.

It helps control recovery work.

---

# 11.2 Crash

Suppose:

```text
Transaction
   ↓
WAL written
   ↓
Server crashes
```

On restart PostgreSQL can use WAL to recover changes that were not fully reflected in data files before the crash.

---

# 11.3 Recovery Mental Model

```text
Database files
+
WAL
      ↓
Crash recovery
      ↓
Consistent database state
```

---

# 11.4 Why Recovery Time Matters

If recovery takes too long:

```text
Application downtime
```

Therefore production systems care about:

* WAL generation
* checkpoint behavior
* storage speed
* recovery time

# CHAPTER 12 — VACUUM, DEAD TUPLES & TABLE BLOAT

This is a critical PostgreSQL operational concept.

---

# 12.1 Why Dead Tuples Exist

Suppose:

```text
UPDATE customer
SET name = 'New Name';
```

Under MVCC, the old row version eventually becomes obsolete.

That creates dead tuple cleanup work.

---

# 12.2 VACUUM

`VACUUM` helps reclaim/reuse space associated with dead tuples and maintains visibility information.

---

# 12.3 Autovacuum

PostgreSQL normally handles routine vacuuming automatically through:

> autovacuum

This is one of the most important background maintenance mechanisms.

---

# 12.4 VACUUM vs VACUUM FULL

Normal:

```sql
VACUUM;
```

is routine maintenance.

`VACUUM FULL` is much more disruptive because it rewrites the table and requires stronger locking.

Do not use `VACUUM FULL` casually in production.

---

# 12.5 Bloat

If obsolete row versions accumulate excessively, tables/indexes can become bloated.

Consequences can include:

```text
more storage
more pages
more I/O
slower scans
```

---

# 12.6 Monitoring

Useful statistics can be found through PostgreSQL system views such as:

```text
pg_stat_user_tables
```

Look for information about:

* live tuples
* dead tuples
* vacuum activity
* analyze activity

---

# CHAPTER 13 — POSTGRESQL INDEX INTERNALS

V03 taught you how indexes affect queries.

Now understand the basic physical idea.

---

# 13.1 B-Tree

PostgreSQL's default index type is:

> B-tree

Conceptually:

```text
              Root
            /      \
          /          \
      branch        branch
       /  \          /  \
     leaf leaf      leaf leaf
```

It supports efficient ordered lookups.

---

# 13.2 Useful Operations

B-tree indexes are useful for many:

```text
=
<
>
<=
>=
ORDER BY
range queries
```

depending on the query and index structure.

---

# 13.3 Hash Index

PostgreSQL also supports hash indexes.

Conceptually:

```text
key
 ↓
hash
 ↓
bucket
```

They are specialized for equality-oriented access.

Don't automatically prefer them over B-tree.

---

# 13.4 GIN

GIN is useful for certain multi-valued or document-oriented search patterns, including some JSONB and full-text-search workloads.

---

# 13.5 GiST

GiST provides a flexible framework useful for specialized data types and search strategies.

---

# 13.6 BRIN

BRIN can be very useful for very large tables where physical row order correlates with the queried values.

For example:

```text
timestamp increases
        ↓
physical storage roughly follows time
```

BRIN can be much smaller than a traditional index in appropriate workloads.

---

# 13.7 Index Trade-Off

Remember:

```text
Index
 ↓
faster reads
 +
storage cost
 +
write/update maintenance
 +
vacuum work
```

Indexing is a workload decision.

---

# CHAPTER 14 — QUERY PLANNER & STATISTICS

PostgreSQL's planner doesn't know the future.

It makes estimates.

---

# 14.1 Why Estimates Matter

Suppose:

```text
Actual matching rows = 500,000
```

but planner estimates:

```text
100
```

It may choose a poor strategy.

---

# 14.2 Statistics

PostgreSQL maintains statistics about table data.

`ANALYZE` updates these statistics.

Autovacuum can also perform automatic analyze operations.

---

# 14.3 ANALYZE

You can explicitly run:

```sql
ANALYZE products;
```

This helps PostgreSQL understand the current data distribution.

---

# 14.4 Data Distribution

Imagine:

```text
status
------
completed = 99%
cancelled = 1%
```

An index on status may not be equally useful for every query.

The planner needs statistical information to make informed decisions.

---

# 14.5 EXPLAIN Investigation

Compare:

```text
estimated rows
actual rows
```

If they're dramatically different, investigate:

* stale statistics
* data skew
* complex predicates
* correlated columns
* planner limitations

# CHAPTER 15 — CONNECTION POOLING

Connection pooling deserves deeper treatment because it directly affects backend architecture.

---

# 15.1 Without Pooling

```text
Request
 ↓
Create DB connection
 ↓
Query
 ↓
Close
```

Repeated thousands of times is inefficient.

---

# 15.2 With Pooling

```text
Application
     ↓
Pool
 ┌───┬───┬───┐
 C1  C2  C3
 └───┴───┴───┘
     ↓
PostgreSQL
```

Requests reuse connections.

---

# 15.3 Pool Size

Too small:

```text
requests wait
```

Too large:

```text
database overloaded
```

The goal is not:

> Maximum possible connections.

The goal is:

> Enough concurrency without overwhelming PostgreSQL.

---

# 15.4 Pooling and Transactions

A connection returned to a pool must not retain an unfinished transaction.

This is why:

```text
idle in transaction
```

can be dangerous.

Application frameworks should correctly:

```text
BEGIN
→ work
→ COMMIT/ROLLBACK
→ release connection
```

# CHAPTER 17 — DATABASE SECURITY & ACCESS CONTROL

Production databases must assume that credentials can be exposed.

Defense in depth matters.

---

# 17.1 Roles

PostgreSQL uses roles for authentication/authorization.

Example:

```sql
CREATE ROLE app_user LOGIN PASSWORD '...';
```

In production, credentials should come from secure secret management rather than being committed to Git.

---

# 17.2 Least Privilege

An application should receive only the permissions it needs.

For example:

```text
Application user
    ↓
SELECT
INSERT
UPDATE
```

rather than unrestricted administrative privileges.

---

# 17.3 Separate Roles

Conceptually:

```text
admin_role
migration_role
application_role
readonly_role
```

Each has a different responsibility.

---

# 17.4 Network Security

Database security includes:

```text
Authentication
Authorization
Network access
Encryption
Secrets
Auditing
```

Not just passwords.

---

# 17.5 Never Expose PostgreSQL Unnecessarily

If your backend is:

```text
Internet
   ↓
API
   ↓
PostgreSQL
```

clients generally should not directly access PostgreSQL.

The application layer controls access.

# CHAPTER 18 — BACKUP & RESTORE ENGINEERING

A backup isn't valuable merely because:

```text
backup file exists
```

A backup is valuable if:

> You can successfully restore it.

---

# 18.1 Logical Backup

PostgreSQL provides:

```bash
pg_dump
```

Example:

```bash
pg_dump -U postgres ecommerce > ecommerce.sql
```

---

# 18.2 Restore

For a SQL-format dump:

```bash
psql -U postgres -d ecommerce_restore < ecommerce.sql
```

---

# 18.3 Custom Format

PostgreSQL supports custom-format dumps that can be restored using:

```bash
pg_restore
```

This gives additional flexibility.

---

# 18.4 Backup Strategy

Think:

```text
What?
When?
Where?
How long?
Encrypted?
Tested?
```

---

# 18.5 Backup Verification

A real backup drill:

```text
Create backup
     ↓
Create clean database
     ↓
Restore backup
     ↓
Run validation queries
     ↓
Compare expected data
```

---

# 18.6 3-2-1 Mental Model

A useful general backup principle:

```text
3 copies
2 different storage/media locations
1 offsite copy
```

The exact implementation depends on the environment.

# CHAPTER 19 — POINT-IN-TIME RECOVERY CONCEPTS

Logical backups alone aren't enough for every production recovery strategy.

Suppose:

```text
Monday 10:00
good state

Monday 15:32
accidental DELETE

Monday 16:00
problem discovered
```

You may want:

> Restore the database to just before 15:32.

This is:

> Point-in-Time Recovery (PITR)

---

# 19.1 Concept

PITR generally combines:

```text
Base backup
+
WAL archives
```

Conceptually:

```text
Base Backup
     ↓
WAL 1
 ↓
WAL 2
 ↓
WAL 3
 ↓
Target time
```

---

# 19.2 Why WAL Matters

This connects:

```text
WAL
+
Backup
+
Recovery
```

into one system.

---

# 19.3 Recovery Objectives

Two important concepts:

## RPO

Recovery Point Objective:

> How much data loss is acceptable?

Example:

```text
RPO = 5 minutes
```

means the recovery design aims to limit potential data loss to around that order of magnitude.

## RTO

Recovery Time Objective:

> How long can recovery take?

Example:

```text
RTO = 30 minutes
```

# CHAPTER 20 — REPLICATION FUNDAMENTALS

Replication means maintaining copies of database state across systems.

---

# 20.1 Primary / Standby

Conceptually:

```text
             Primary
                │
              WAL
                ↓
             Standby
```

---

# 20.2 Why Replicate?

Potential purposes:

* high availability
* disaster recovery
* read scaling
* operational resilience

These are different goals.

---

# 20.3 Streaming Replication

PostgreSQL can stream WAL changes from a primary to a standby.

Conceptually:

```text
Primary
  ↓
WAL
  ↓
network
  ↓
Standby
  ↓
replay
```

---

# 20.4 Replication Lag

Standby may temporarily be behind primary.

```text
Primary:
LSN 1000

Standby:
LSN 950
```

The difference represents lag in progress.

---

# 20.5 Important Lesson

A replica is not automatically:

> A backup.

Replication can copy:

```text
bad data
```

too.

If an accidental delete is replicated, the replica can also receive it.

Therefore:

```text
Replication
≠
Backup
```

You may need both.

# CHAPTER 22 — PARTITIONING

Partitioning divides a large logical table into smaller physical pieces.

---

# 22.1 Why?

Imagine:

```text
orders
500 million rows
```

Maybe partition by time:

```text
orders_2026_01
orders_2026_02
orders_2026_03
...
```

---

# 22.2 Range Partitioning

Common for time-based data.

Conceptually:

```text
2026-01
2026-02
2026-03
```

---

# 22.3 List Partitioning

Partition according to discrete categories.

Example:

```text
region = south
region = north
```

---

# 22.4 Hash Partitioning

Distribute rows according to a hash.

Useful in some workloads where balanced distribution matters.

---

# 22.5 Partition Pruning

If a query asks:

```sql
WHERE created_at >= '2026-01-01'
  AND created_at < '2026-02-01'
```

PostgreSQL may only need to access relevant partitions.

---

# 22.6 Don't Partition Everything

Partitioning introduces complexity.

Use it when:

```text
table size
+
workload
+
maintenance requirements
```

justify it.
